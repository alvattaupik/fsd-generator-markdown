# 1 Deskripsi Use Case

**Tabel 1: Deskripsi Use Case Generate Report Web POS**

| Elemen Spesifikasi | Deskripsi Detail |
| --- | --- |
| ID Use Case | UC-WPOS-007 |
| Nama Use Case | Generate Report Web POS |
| Penjelasan Singkat | Fitur Aplikasi Web POS yang memungkinkan User Kasir / Staff Merchant mengajukan permintaan generasi laporan transaksi penjualan kasir secara latar belakang (*background process*) dengan pilihan filter preset atau rentang tanggal kustom, menyaring data secara WAJIB berdasarkan `merchant_id`, menyimpan metadata ke `report_generator` dan `report_generator_filters`, membentuk berkas fisik berformat `.xlsx` atau `.pdf`, serta mengunggahnya ke S3 Storage pada folder `reports/`. |
| Aktor Utama | User Kasir (Kasir Web POS / Staff Merchant) |
| Aktor Pendukung | Report Engine, AWS S3 Storage |
| Deskripsi Singkat | User Kasir melakukan otentikasi login ke Aplikasi Web POS dan mengakses menu **Laporan Kasir** -> **Generate Report**. User Kasir memilih jenis laporan yang akan ditarik (seperti Laporan Penjualan Kasir, Laporan Shift Transaksi, Laporan Ringkasan POS, dll.), menentukan format berkas keluaran (`.xlsx` atau `.pdf`), serta menentukan pilihan filter periode. Filter yang didukung meliputi Preset **Hari Ini**, **7 Hari Terakhir**, **1 Bulan Terakhir** (Periode Default), dan **1 Tahun Terakhir**, maupun **Custom Range Date** dengan rentang maksimum 1 tahun (12 bulan) terakhir. Saat User Kasir mengklik **"Generate Report"**, Report Engine memvalidasi masukan, meng-insert record ke tabel **`report_generator`** dengan status awal `request_status = 'REQUESTED'`, dan menyimpan parameter ke **`report_generator_filters`**. Selanjutnya, background worker pada Report Engine mengambil antrean job, mengubah status menjadi `request_status = 'IN_PROCESS'`, mengeksekusi kueri data dari database **secara WAJIB memfilter berdasarkan `merchant_id`** (disertai `store_id`/`terminal_id`), serta membentuk berkas fisik laporan (`.xlsx` atau `.pdf`). Berkas laporan diunggah ke AWS S3 Storage pada direktori folder **`reports/`**. Setelah unggah berhasil, Report Engine memperbarui `file_url` dan meng-update status menjadi `request_status = 'COMPLETED'`. Apabila terjadi kegagalan atau exception selama pemrosesan, status di-update menjadi `request_status = 'ERROR'`. |
| Pre-condition | 1. User Kasir telah berhasil login ke Aplikasi Web POS dan memiliki sesi kasir/toko yang aktif dengan `merchant_id` yang valid.<br>2. Layanan AWS S3 Storage dan Report Engine background worker beroperasi secara aktif. |
| Post-condition | 1. Metadata permintaan generasi laporan kasir tersimpan pada tabel `report_generator` dan `report_generator_filters`.<br>2. Berkas fisik laporan berformat `.xlsx` atau `.pdf` berhasil dibentuk dan diunggah ke AWS S3 Storage pada folder `reports/`.<br>3. Status `request_status` pada tabel `report_generator` diperbarui menjadi `COMPLETED` (atau `ERROR` jika gagal) beserta `file_url` yang siap diunduh oleh User Kasir. |
| Trigger | User Kasir memilih jenis laporan, menentukan filter periode & format berkas pada menu Generate Report Web POS, lalu mengklik tombol **"Generate Report"**. |
| Nama Tabel | report_generator, report_generator_filters |
| Integrasi | 1. **Web POS App UI:** Antarmuka formulir pengajuan laporan kasir dan tabel riwayat pemrosesan report.<br>2. **Report Engine:** Microservice backend pengelola antrean request dan eksekutor generasi berkas laporan background.<br>3. **AWS S3 Storage (Doc Storage):** Media penyimpanan objek berkas fisik hasil generasi laporan (`reports/`). |
| Asumsi | 1. Generasi laporan dilakukan secara asinkron (*background job*) untuk menjaga kelancaran operasional kasir di Web POS.<br>2. Berkas laporan yang diunduh WAJIB difilter secara ketat berdasarkan `merchant_id` (serta `store_id` / `terminal_id`) akun merchant yang sedang aktif di Web POS. |
| Keterbatasan | 1. Rentang tanggal kustom (*Custom Range Date*) dibatasi maksimal 1 tahun (12 bulan atau 365 hari) ke belakang.<br>2. Format file keluaran yang didukung terbatas pada format spreadsheet `.xlsx` dan dokumen `.pdf`. |
| Aturan Bisnis/Sistem | 1. **Preset Period & Range Filter Standard:** Sistem WAJIB menyediakan 4 opsi filter preset acuan:<br>&nbsp;&nbsp;- **Hari Ini:** Menampilkan transaksi/penjualan kasir untuk hari berjalan.<br>&nbsp;&nbsp;- **7 Hari Terakhir:** Menampilkan data 7 hari ke belakang.<br>&nbsp;&nbsp;- **1 Bulan Terakhir:** Menampilkan data 30 hari ke belakang (periode default).<br>&nbsp;&nbsp;- **1 Tahun Terakhir:** Menampilkan data 365 hari ke belakang.<br>&nbsp;&nbsp;- **Custom Range Date:** Maksimum rentang tanggal mulai hingga tanggal akhir adalah 1 tahun (12 bulan).<br>2. **Mandatory Merchant Scope Isolation:** Kueri generasi laporan penjualan pada Web POS **WAJIB menyertakan filter `merchant_id`** (disertai opsional `store_id` atau `terminal_id`) sesuai dengan merchant tempat kasir bertugas.<br>3. **Request Lifecycle Status Standard:** Lifecycle status pada tabel `report_generator` dibatasi pada enum resmi:<br>&nbsp;&nbsp;- **`REQUESTED`**: Diset saat request pertama kali dibuat dan tersimpan di database.<br>&nbsp;&nbsp;- **`IN_PROCESS`**: Diset saat background worker mulai mengeksekusi kueri dan membuat berkas.<br>&nbsp;&nbsp;- **`COMPLETED`**: Diset saat berkas `.xlsx`/`.pdf` berhasil diunggah ke S3 Storage.<br>&nbsp;&nbsp;- **`ERROR`**: Diset jika terjadi crash, timeout, atau kegagalan generasi berkas/upload.<br>4. **S3 Storage Storage Path Standard:** Berkas hasil generasi WAJIB disimpan pada AWS S3 Storage dalam struktur direktori folder `reports/pos/{merchant_id}/{store_id}/{year}/{report_id}.{ext}`.<br>5. **Supported Export Formats:** Sistem memfasilitasi dua pilihan format ekspor resmi yaitu `.xlsx` (Microsoft Excel) dan `.pdf` (Portable Document Format).<br>10. **Web POS Request Signature Verification Standard:** Selain permintaan Aktivasi (UC-WPOS-001), seluruh permintaan API yang dikirimkan oleh peramban Web POS WAJIB ditandatangani secara digital (*digital signature* - header X-Signature) menggunakan Private Key yang tersimpan pada *Local Device Storage* peramban (*IndexedDB / Hardware TPM*). API Gateway WAJIB memverifikasi signature tersebut menggunakan web_pos_public_key yang tersimpan pada tabel mst_merchant_terminals (atau Redis Cache). Apabila signature tidak valid, kedaluwarsa, atau missing, API Gateway WAJIB menolak request secara langsung (HTTP Status 401 INVALID_DEVICE_SIGNATURE).  |

# 2 Main Flow

**Tabel 2: Main Flow Generate Report Web POS**

| No. | Aktivitas | Deskripsi |
| ---: | --- | --- |
| 1 | Membuka Menu Generate Report | User Kasir melakukan login ke Aplikasi Web POS dan mengklik menu **Laporan Kasir** -> **Generate Report**. |
| 2 | Menampilkan Form Request Laporan | Sistem menampilkan formulir pengajuan laporan kasir beserta tabel riwayat permintaan laporan sebelumnya. |
| 3 | Memilih Jenis Report & Format File | User Kasir memilih jenis laporan (misal: Laporan Penjualan Kasir) dan memilih format keluaran berkas (`.xlsx` atau `.pdf`). |
| 4 | Memilih Filter Periode | User Kasir memilih preset filter (**Hari Ini**, **7 Hari Terakhir**, **1 Bulan Terakhir**, **1 Tahun Terakhir**) atau mengisi **Custom Range Date** (maksimal 1 tahun). |
| 5 | Mengirim Request Generasi Laporan | User Kasir mengklik tombol **"Generate Report"**. |
| 6 | Memvalidasi & Simpan Request | Front-End memvalidasi masukan dan mengirim request ke API Gateway. Report Engine meng-insert header ke `report_generator` (`request_status = 'REQUESTED'`) dan detail filter ke `report_generator_filters`. |
| 7 | Menampilkan Konfirmasi Antrean | Front-End menampilkan notifikasi bahwa permintaan laporan telah diterima dan masuk ke dalam antrean *background job*. |
| 8 | Memulai Background Worker | Background Worker pada Report Engine mengonsumsi antrean job, lalu meng-update `report_generator` menjadi `request_status = 'IN_PROCESS'`. |
| 9 | Mengolah Data & Membentuk File | Report Engine mengeksekusi kueri data penjualan dari database **secara WAJIB dengan filter `merchant_id`** (serta `store_id` / `terminal_id`) dan membentuk berkas fisik laporan dalam format `.xlsx` atau `.pdf`. |
| 10 | Mengunggah Berkas ke S3 Storage | Report Engine mengunggah berkas fisik laporan ke AWS S3 Storage pada direktori folder `reports/pos/` dan memperoleh `file_url`. |
| 11 | Update Status Completed | Report Engine memperbarui `file_url` dan meng-update status pada `report_generator` menjadi `request_status = 'COMPLETED'`. |
| 12 | Use Case Selesai | Berkas laporan kasir berhasil digenerate dan siap diunduh oleh User Kasir melalui tombol "Download" pada tabel riwayat. |

# 3 Alternative Flow

**Tabel 3: Alternative Flow Generate Report Web POS**

| Kode | Alternative Flow | Deskripsi |
| --- | --- | --- |
| AF-01 | Custom Range Date Melebihi 1 Tahun | Pada langkah 4-5, apabila User Kasir memilih *Custom Range Date* dengan selisih rentang tanggal melebihi 1 tahun (12 bulan), Sistem menolak request dan Front-End menampilkan `Rentang tanggal pencarian laporan maksimum 1 tahun terakhir`. |
| AF-02 | Kegagalan Pemrosesan Background / Storage Error | Pada langkah 9-10, apabila terjadi exception saat pembuatan berkas atau gagal terhubung ke AWS S3 Storage, Report Engine meng-update status pada `report_generator` menjadi `request_status = 'ERROR'` dan mencatat error log. |
| AF-03 | Data Laporan Kasir Kosong | Pada langkah 9, apabila kueri data laporan kasir tidak menghasilkan record data untuk `merchant_id` tersebut, Report Engine tetap membentuk berkas template kosong dengan header data, mengunggah ke S3, dan memperbarui `request_status = 'COMPLETED'`. |

# 4 Status Front-End

**Tabel 4: Status Front-End Generate Report Web POS**

| No. | Nama Status | Deskripsi Tampilan Front-End |
| ---: | --- | --- |
| 1 | IDLE | Formulir pengajuan report generator siap menerima input jenis laporan, filter periode, dan format berkas. |
| 2 | REQUESTED | Badge status berwarna abu-abu pada tabel riwayat menunjukkan permintaan baru tersimpan dan antre diproses. |
| 3 | IN_PROCESS | Badge status berwarna biru disertai animasi *spinner* pada tabel riwayat menunjukkan berkas sedang digenerate. |
| 4 | COMPLETED | Badge status berwarna hijau pada tabel riwayat beserta tombol **"Download"** aktif untuk mengunduh berkas (.xlsx / .pdf). |
| 5 | ERROR | Badge status berwarna merah pada tabel riwayat menunjukkan pemrosesan generasi laporan mengalami kegagalan. |

# 6 Sequence Diagram Generate Report Web POS

```plantuml
@startuml
title Sequence Diagram - Generate Report Web POS

actor "User Kasir" as user
boundary "Front-End" as fe
control "API Gateway" as gateway
control "Report Engine" as service
database "QRIS Database" as db
participant "AWS S3 Storage" as s3

user -> fe : Buka Menu Generate Report & Isi Formulir\n(Jenis Report, Format .xlsx/.pdf, Filter Periode)
user -> fe : Klik Tombol "Generate Report"

alt Custom Date Range > 1 Tahun [AF-01]
  fe --> user : Tampilkan Error "Rentang tanggal pencarian laporan maksimum 1 tahun terakhir"
else Validasi Filter Valid
  fe -> gateway : POST /api/v1/pos/reports/generate (Payload Filter & Format)
  gateway -> service : Teruskan Request Generate Report POS
  
  service -> db : Insert report_generator (request_status = 'REQUESTED')
  db --> service : Return report_id
  
  service -> db : Insert report_generator_filters
  db --> service : Confirm Filters Saved
  
  service --> gateway : Response Request Accepted (HTTP 202 Accepted)
  gateway --> fe : Response Request Accepted (HTTP 202 Accepted)
  fe --> user : Tampilkan Notifikasi "Permintaan Laporan Diterima" & Tampilkan Status REQUESTED

  note over service : Pemrosesan Background Job secara Asinkron

  service -> db : Update report_generator (request_status = 'IN_PROCESS')
  db --> service : Confirm Status IN_PROCESS

  service -> db : Query Data Laporan Penjualan (WAJIB Filter BY merchant_id & store_id)
  db --> service : Return Data Record Kasir

  service -> service : Formasi Berkas Fisik (.xlsx atau .pdf)

  alt Error Saat Generasi / Upload S3 [AF-02]
    service -> db : Update report_generator (request_status = 'ERROR')
  else Generasi Berkas & Upload Sukses
    service -> s3 : Upload Berkas Fisik ke Folder reports/pos/
    s3 --> service : Return Presigned S3 File URL
    
    service -> db : Update report_generator\n(file_url, request_status = 'COMPLETED')
    db --> service : Confirm Status COMPLETED

    fe -> gateway : GET /api/v1/pos/reports/history (Polling / Refresh)
    gateway -> service : Teruskan Request Status History
    service -> db : Query Status report_generator
    db --> service : Return Status COMPLETED & file_url
    service --> gateway : Response History Data
    gateway --> fe : Response History Data
    fe --> user : Tampilkan Badge COMPLETED & Tombol "Download" Aktif
  end
end
@endl
```
