# 1 Deskripsi Use Case

**Tabel 1: Deskripsi Use Case Blokir User Kasir**

| Elemen Spesifikasi | Deskripsi Detail |
| --- | --- |
| ID Use Case | UC-BOH-027 |
| Nama Use Case | Blokir User Kasir |
| Penjelasan Singkat | Fitur Web Back Office Hibank yang memfasilitasi User Bank untuk meninjau rincian pengguna merchant, memfilter akun ber-role `KASIR` (atau kasir merchant), dan memblokir secara langsung akun user kasir pada tabel `mst_users` (`login_status = 'BLOCKED'`) melalui service `merchant_managements`, sehingga Kasir tersebut tidak dapat melakukan login ke Aplikasi POS / Mobile POS. |
| Aktor Utama | User Bank (Back Office Hibank Staff / Operations / Support) |
| Aktor Pendukung | merchant_managements (Merchant Management Service) |
| Deskripsi Singkat | User Bank melakukan otentikasi login SSO ke Web Back Office Hibank dan mengakses menu **Merchant Management** -> **Monitor Merchant Users**. Sistem menampilkan daftar merchant terdaftar. User Bank memilih salah satu merchant, lalu mengklik tombol **"Details"**. Sistem menampilkan modal/halaman rincian daftar pengguna yang terdaftar pada merchant tersebut dari tabel `mst_users` dan `mst_roles`. User Bank memfilter atau memilih akun pengguna yang memiliki peran **`KASIR`** (dari `mst_roles`), lalu mengklik tombol aksi **"Blokir"**. Sistem menampilkan modal konfirmasi pemblokiran yang meminta pengisian alasan pemblokiran (*blocking reason*). User Bank memasukkan alasan pemblokiran dan mengklik tombol **"Konfirmasi Pemblokiran"**. Front-End mengirim request ke API Gateway. Service `merchant_managements` memvalidasi status akun. Setelah validasi sukses, service secara langsung memperbarui status akun kasir pada tabel **`mst_users`** menjadi **`login_status = 'BLOCKED'`** dan mencatat alasan pemblokiran, sehingga kasir ditolak saat mencoba login ke Aplikasi POS. Front-End memperbarui status pada modal rincian user dan menampilkan konfirmasi bahwa akun user kasir berhasil diblokir. |
| Pre-condition | 1. User Bank telah berhasil login SSO ke Web Back Office Hibank dan memiliki otoritas kewenangan *Merchant User Administrator*.<br>2. Akun user kasir yang akan diblokir terdaftar aktif pada tabel `mst_users` (`login_status = 'ACTIVE'`). |
| Post-condition | 1. Kolom `login_status` akun user kasir pada tabel `mst_users` diperbarui secara langsung menjadi `BLOCKED`.<br>2. Kasir yang diblokir ditolak akses autentikasinya dan tidak dapat melakukan login ke Aplikasi Web POS / Mobile POS.<br>3. Front-End memperbarui status tampilan akun kasir pada modal rincian pengguna merchant. |
| Trigger | User Bank mengklik tombol **"Details"** pada merchant terpilih, memfilter role `KASIR`, mengklik tombol **"Blokir"**, mengisi alasan pemblokiran, dan mengklik **"Konfirmasi Pemblokiran"**. |
| Nama Tabel | mst_users, mst_roles |
| Integrasi | 1. **Web Back Office Hibank UI:** Antarmuka daftar merchant, modal rincian pengguna merchant, dan dialog pemblokiran akun Kasir.<br>2. **merchant_managements:** Microservice backend pengelola pembaruan status keaktifan akun merchant secara langsung di database. |
| Asumsi | 1. Pemblokiran kasir dilakukan secara langsung di database tanpa memerlukan penerbitan event Kafka.<br>2. Pemblokiran kasir hanya berdampak pada akun individu kasir tersebut dan tidak memblokir merchant induk atau pengguna lainnya. |
| Keterbatasan | 1. Akun kasir yang sudah berstatus `login_status = 'BLOCKED'` tidak dapat diblokir ulang.<br>2. Pengisian alasan pemblokiran bersifat mandatori untuk kebutuhan jejak audit (*audit trail*). |
| Aturan Bisnis/Sistem | 1. **Role Filtering Standard:** User Bank dapat melihat dan memilih spesifik akun ber-role `KASIR` dari relasi tabel `mst_roles`.<br>2. **Direct User Status Update Standard:** Service `merchant_managements` WAJIB meng-update kolom `login_status = 'BLOCKED'` pada `mst_users` khusus untuk `user_id` kasir terpilih.<br>3. **Authentication Access Denial:** Akun Kasir dengan `login_status = 'BLOCKED'` WAJIB ditolak oleh sistem otentikasi saat mencoba melakukan login ke Web POS / Mobile POS.<br>4. **Mandatory Blocking Reason:** Pengisian kolom alasan pemblokiran (*blocking_reason*) bersifat WAJIB sebelum eksekusi pemblokiran diproses.<br>5. **Audit Trail Standard:** Setiap tindakan pemblokiran kasir mencatat `user_id` kasir, `blocked_by` (ID User Bank), alasan pemblokiran, dan timestamp pada `mst_users`. |
| Session Idle | 15 Menit |

# 2 Main Flow

**Tabel 2: Main Flow Blokir User Kasir**

| No. | Aktivitas | Deskripsi |
| ---: | --- | --- |
| 1 | Membuka Menu Monitor Merchant Users | User Bank melakukan login SSO dan mengklik menu **Merchant Management** -> **Monitor Merchant Users**. |
| 2 | Menampilkan Daftar Merchant | Sistem menampilkan tabel daftar merchant dari database beserta tombol aksi **"Details"** per baris merchant. |
| 3 | Memilih Tombol Details | User Bank mengklik tombol **"Details"** pada salah satu baris merchant terpilih. |
| 4 | Menampilkan Detail User Merchant | Sistem menampilkan modal rincian daftar pengguna yang terdaftar di bawah merchant tersebut dari `mst_users` dan `mst_roles`. |
| 5 | Memfilter Role Kasir | User Bank memfilter atau memilih akun pengguna ber-role **`KASIR`**. |
| 6 | Memilih Tombol Blokir Kasir | User Bank mengklik tombol aksi **"Blokir"** pada baris akun user kasir terpilih. |
| 7 | Menampilkan Modal Pemblokiran | Sistem menampilkan modal konfirmasi pemblokiran yang memuat rincian nama kasir, email/username kasir, dan textarea alasan pemblokiran. |
| 8 | Mengisi Alasan & Konfirmasi | User Bank menginput alasan pemblokiran pada kolom textarea dan mengklik tombol **"Konfirmasi Pemblokiran"**. |
| 9 | Memvalidasi Request Pemblokiran | Front-End memvalidasi ketersediaan alasan dan mengirim request pemblokiran kasir ke API Gateway. |
| 10 | Direct Update Status Kasir | Service `merchant_managements` langsung memperbarui akun kasir pada `mst_users` (`login_status = 'BLOCKED'`, `blocking_reason`). |
| 11 | Menampilkan Konfirmasi Berhasil | Front-End memperbarui modal rincian user dan menampilkan notifikasi bahwa akun user kasir telah berhasil diblokir. |

# 3 Alternative Flow

**Tabel 3: Alternative Flow Blokir User Kasir**

| Kode | Alternative Flow | Deskripsi |
| --- | --- | --- |
| AF-01 | Alasan Pemblokiran Kosong | Pada langkah 8-9, apabila User Bank mengosongkan kolom alasan pemblokiran, Sistem menolak request dan Front-End menampilkan `Alasan pemblokiran kasir wajib diisi`. |
| AF-02 | Akun Kasir Sudah Berstatus Blocked | Pada langkah 10, apabila akun kasir pada database sudah berstatus `login_status = 'BLOCKED'`, Sistem membatalkan transaksi dan Front-End menampilkan `Akun kasir sudah dalam status diblokir`. |
| AF-03 | Gagal Terhubung ke Database Server | Pada langkah 10, apabila koneksi database terputus total, Sistem mengembalikan HTTP status 500 dan Front-End menampilkan `Gagal memperbarui status pemblokiran kasir ke database`. |

# 6 Sequence Diagram Blokir User Kasir

```plantuml
@startuml
title Sequence Diagram - Blokir User Kasir

actor "User Bank" as user
boundary "Front-End" as fe
control "API Gateway" as gateway
control "merchant_managements" as service
database "QRIS Database" as db

user -> fe : Akses Menu Monitor Merchant Users & Klik "Details"
fe -> gateway : Request Get Merchant Users List
gateway -> service : Teruskan Request Get Merchant Users List
service -> db : Query mst_users JOIN mst_roles BY merchant_id
db --> service : Return Data Users List & Roles
service --> gateway : Response Users List
gateway --> fe : Response Users List
fe --> user : Tampilkan Modal Detail User Merchant

user -> fe : Filter Role "KASIR" & Klik "Blokir" pada Row Kasir
fe --> user : Tampilkan Modal Form Pemblokiran Kasir (Input Reason)

user -> fe : Input Alasan Pemblokiran & Klik "Konfirmasi Pemblokiran"
fe -> fe : Validasi Client-side (Alasan Mandatory)

alt Alasan Kosong [AF-01]
  fe --> user : Tampilkan Pesan "Alasan pemblokiran kasir wajib diisi"
else Form Valid
  fe -> gateway : Request Block User Kasir (Payload: reason)
  gateway -> service : Teruskan Request Block User Kasir
  
  service -> db : Query login_status kasir pada mst_users
  db --> service : Return Data Kasir Status
  
  alt Kasir Sudah BLOCKED [AF-02]
    service --> gateway : Response Error (HTTP 400 Bad Request)
    gateway --> fe : Response Error (HTTP 400 Bad Request)
    fe --> user : Tampilkan Pesan "Akun kasir sudah dalam status diblokir"
  else Kasir Valid & ACTIVE
    service -> db : Update mst_users (login_status = 'BLOCKED', blocking_reason, updated_at) WHERE user_id = kasir_user_id
    db --> service : Confirm Update Kasir User Status
    
    service --> gateway : Response Sukses (HTTP 200 OK)
    gateway --> fe : Response Sukses (HTTP 200 OK)
    fe --> user : Tampilkan Notifikasi Sukses & Refresh Modal Detail User Merchant
  end
end
@enduml
```
