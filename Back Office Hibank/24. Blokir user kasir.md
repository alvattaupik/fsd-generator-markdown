# 1 Deskripsi Use Case

**Tabel 1: Deskripsi Use Case Blokir User Kasir**

| Elemen Spesifikasi | Deskripsi Detail |
| --- | --- |
| ID Use Case | UC-BOH-024 |
| Nama Use Case | Blokir User Kasir |
| Penjelasan Singkat | Fitur Web Back Office Hibank pada menu App Config -> Users Management (Tab User Merchant) yang memfasilitasi User Bank untuk memfilter akun pengguna berdasarkan Nama Merchant dan Role `KASIR`, serta mengubah status akun user kasir menjadi `Blocked` pada tabel `mst_users` (`login_status = BLOCKED`), sehingga user kasir tersebut tidak dapat melakukan login ke Portal Merchant maupun Web POS / Mobile App POS. |
| Aktor Utama | User Bank (Back Office Hibank Compliance / Risk / Operations Staff) |
| Aktor Pendukung | System Management Service (`system_management_service`) |
| Deskripsi Singkat | User Bank melakukan otentikasi login SSO ke Web Back Office Hibank dan mengakses menu **App Config** -> **Users Management**. Sistem menampilkan halaman pengelolaan pengguna dengan beberapa tab. User Bank memilih tab **User Merchant**. Sistem menyajikan toolbar pencarian dan filter data. User Bank memasukkan/memilih kriteria filter berdasarkan **Nama Merchant** (pada kolom pencarian/select merchant) dan memilih opsi filter Role **`KASIR`** (pada dropdown filter role). Sistem menampilkan daftar akun pengguna merchant yang memenuhi kriteria filter dari tabel `mst_users`, `mst_merchants`, dan `mst_roles`. User Bank memilih baris akun user kasir yang akan diblokir, lalu mengklik tombol aksi **"Edit"**. Sistem menampilkan modal/halaman formulir pengeditan data pengguna merchant. User Bank mengubah pilihan kolom Status Pengguna dari `Active` menjadi **`Blocked`** dan menginputkan Alasan Pemblokiran (*blocking reason*). User Bank mengklik tombol **"Simpan Data"**. Front-End memvalidasi kelengkapan data dan mengirimkan request pemblokiran ke API Gateway. Service `system_management_service` memvalidasi keberadaan `user_id`. Setelah validasi sukses, service secara langsung memperbarui status akun user kasir pada tabel **`mst_users`** menjadi **`login_status = BLOCKED`** dan mencatat jejak pemblokiran ke tabel **`audit_logs`**, sehingga akun kasir ditolak saat mencoba autentikasi login ke Web POS / Mobile App POS. Front-End memperbarui tabel daftar user merchant dan menampilkan notifikasi konfirmasi bahwa akun user kasir berhasil diblokir. |
| Pre-condition | 1. User Bank telah berhasil login SSO ke Web Back Office Hibank dan memiliki hak akses menu *App Config - Users Management*.<br>2. Akun user kasir yang akan diblokir terdaftar aktif pada tabel `mst_users` (`login_status = ACTIVE`). |
| Post-condition | 1. Kolom `login_status` akun user kasir pada tabel `mst_users` diperbarui secara langsung menjadi `BLOCKED`.<br>2. User kasir yang diblokir ditolak akses autentikasinya dan tidak dapat melakukan login ke Web POS / Mobile App POS.<br>3. Front-End memperbarui tampilan tabel daftar user merchant pada tab User Merchant menu App Config. |
| Trigger | User Bank mengakses menu **App Config** -> **Users Management**, memilih tab **User Merchant**, memfilter **Nama Merchant** dan Role **`KASIR`**, mengklik tombol **"Edit"**, mengubah status menjadi **`Blocked`**, mengisi alasan pemblokiran, dan mengklik **"Simpan Data"**. |
| Nama Tabel | mst_users, mst_roles, mst_merchants, audit_logs |
| Integrasi | 1. **Web Back Office Hibank UI:** Antarmuka menu App Config - Users Management (Tab User Merchant), filter toolbar, dan form edit user merchant.<br>2. **System Management Service:** Microservice backend pengelola pembaruan status keaktifan dan otorisasi pengguna merchant di database. |
| Asumsi | 1. Pemblokiran akun user kasir berfokus khusus pada penangguhan hak akses login kasir ke aplikasi kasir (Web POS / Mobile App POS).<br>2. Alasan pemblokiran dicatat secara eksplisit pada log perubahan untuk kebutuhan *audit trail*. |
| Keterbatasan | 1. Akun user kasir berstatus `BLOCKED` tidak dapat dipulihkan kecuali dilakukan aksi *Unblock* dari menu App Config.<br>2. Pemblokiran akun kasir spesifik tidak mempengaruhi hak akses akun Merchant Owner atau kasir lain di bawah merchant yang sama. |
| Aturan Bisnis/Sistem | 1. **Navigation & Scoping:** Fitur pemblokiran user kasir dikelola terpusat pada menu **App Config** -> sub-menu **Users Management** -> tab **User Merchant**.<br>2. **Filter & Search Criteria:** Toolbar filter mendukung pencarian spesifik berbasis **Nama Merchant** (`merchant_name`) dan pemfilteran peran **`KASIR`** (`role_code = KASIR`).<br>3. **Edit Form Status Modification:** Perubahan status dilakukan melalui form Edit User Merchant dengan mengubah field Status dari `Active` menjadi `Blocked` serta mengisi field wajib `Blocking Reason`.<br>4. **Direct Database Update (`mst_users`):** Sistem memperbarui kolom `login_status = BLOCKED`, `updated_at`, dan `updated_by` pada tabel `mst_users`.<br>5. **Authentication Lockout:** Sistem autentikasi POS secara otomatis menolak permintaan login dari akun yang memiliki `login_status = BLOCKED`.<br>6. **Audit Trail Logging:** Setiap tindakan pemblokiran wajib mencatat ID pelaksana, timestamp, ID merchant, dan alasan pemblokiran ke tabel `audit_logs`. |
| Session Idle | 15 Menit |

# 3 Alternative Flow

**Tabel 3: Alternative Flow Blokir User Kasir**

| Kode | Alternative Flow | Deskripsi |
| --- | --- | --- |
| AF-01 | Alasan Pemblokiran Kosong | Pada langkah 8-9, apabila User Bank mengosongkan kolom alasan pemblokiran saat memilih status `Blocked`, Sistem menolak request dan Front-End menampilkan pesan `Alasan pemblokiran kasir wajib diisi`. |
| AF-02 | Akun Kasir Sudah Berstatus Blocked | Pada langkah 10, apabila akun kasir pada database sudah berstatus `login_status = BLOCKED`, Sistem membatalkan transaksi dan Front-End menampilkan `Akun kasir sudah dalam status diblokir`. |
| AF-03 | Gagal Terhubung ke Database Server | Pada langkah 10, apabila koneksi database terputus total, Sistem mengembalikan HTTP status 500 dan Front-End menampilkan `Gagal memperbarui status pemblokiran kasir ke database`. |

# 6 Sequence Diagram Blokir User Kasir

```plantuml
@startuml
title Sequence Diagram - Blokir User Kasir

actor "User Bank" as user
boundary "Front-End" as fe
control "API Gateway" as gateway
control "System Management Service" as service
database "QRIS Database" as db

user -> fe : Akses App Config -> Users Management -> Tab User Merchant
user -> fe : Filter Nama Merchant & Select Role "KASIR"
fe -> gateway : Request Get Merchant Users List (merchant_name, role=KASIR)
gateway -> service : Teruskan Request Get Merchant Users List
service -> db : Query mst_users JOIN mst_merchants JOIN mst_roles
db --> service : Return Data Users List & Roles
service --> gateway : Response Users List
gateway --> fe : Response Users List
fe --> user : Tampilkan Daftar User Kasir

user -> fe : Klik Tombol "Edit" pada Row Kasir
fe --> user : Tampilkan Form Edit User Merchant

user -> fe : Pilih Status "Blocked", Input Alasan & Klik "Simpan Data"
fe -> fe : Validasi Client-side (Alasan Mandatory)

alt Alasan Kosong [AF-01]
  fe --> user : Tampilkan Pesan "Alasan pemblokiran kasir wajib diisi"
else Form Valid
  fe -> gateway : Request Update User Status (Payload: status=BLOCKED, reason)
  gateway -> service : Teruskan Request Update User Status
  
  service -> db : Query login_status kasir pada mst_users
  db --> service : Return Data Kasir Status
  
  alt Kasir Sudah BLOCKED [AF-02]
    service --> gateway : Response Error (HTTP 400 Bad Request)
    gateway --> fe : Response Error (HTTP 400 Bad Request)
    fe --> user : Tampilkan Pesan "Akun kasir sudah dalam status diblokir"
  else Kasir Valid & ACTIVE
    service -> db : Update mst_users (login_status = BLOCKED, blocking_reason, updated_at) WHERE user_id = kasir_user_id
    service -> db : Insert audit_logs (action=BLOCK_USER_KASIR, user_id)
    db --> service : Confirm Update Kasir User Status
    
    service --> gateway : Response Sukses (HTTP 200 OK)
    gateway --> fe : Response Sukses (HTTP 200 OK)
    fe --> user : Tampilkan Notifikasi Sukses & Refresh Tabel User Merchant
  end
end
@endl
```
