# 1 Deskripsi Use Case

**Tabel 1: Deskripsi Use Case Monitoring Refund Transaksi**

| Elemen Spesifikasi | Deskripsi Detail |
| --- | --- |
| ID Use Case | UC-BOH-043 |
| Nama Use Case | Monitoring Refund Transaksi |
| Penjelasan Singkat | Fitur Back Office Hibank pada menu Dispute & Refund Management yang memfasilitasi tim Operasional / Officer Bank Hibank untuk memantau seluruh daftar pengajuan pengembalian dana (*refund requests*) dari merchant, memfilter status refund (`IN_REVIEW`, `APPROVED_BY_BANK`, `REJECTED_BY_BANK`, `APPROVED_ISSUER`, `REJECTED_BY_ISSUER`), serta melihat rincian riwayat pelacakan (*refund tracking timeline*) 6 tahap (SUBMITTED, PEMERIKSAAN, PERSETUJUAN, MENGIRIMKAN REQUEST KE ISSUER, TANGGAPAN ISSUER: REJECTED/APPROVED, DANA DIKEMBALIKAN) dari tabel `refunds`, `refund_tracking`, dan `transaction_qris` melalui Dispute Management Service. |
| Aktor Utama | Officer Bank / Tim Operasional Hibank |
| Aktor Pendukung | Dispute Management Service, Apache Kafka Broker |
| Deskripsi Singkat | Officer Bank Hibank melakukan otentikasi login SSO ke Back Office Hibank dan mengakses menu **Dispute & Refund Management** -> **Monitoring Refund Transaksi**. Sistem menampilkan halaman pemantauan refund global yang memuat seluruh pengajuan refund dari berbagai merchant pada tabel `refunds`. Halaman dilengkapi filter pencarian multi-parameter (Merchant ID, Nama Merchant, ID Refund, RRN, Tanggal) dan filter status (`IN_REVIEW`, `APPROVED_BY_BANK`, `REJECTED_BY_BANK`, `APPROVED_ISSUER`, `REJECTED_BY_ISSUER`). Officer Bank mengklik tombol **"Detail"** pada salah satu baris pengajuan refund. Front-End mengirim request ke API Gateway. **Dispute Management Service** mengambil detail rincian pengajuan dari tabel `refunds` yang digabungkan dengan tabel `transaction_qris` serta seluruh riwayat *timeline* pelacakan dari tabel `refund_tracking`. Sistem menampilkan modal/halaman rincian detail refund yang menyajikan informasi komprehensif transaksi QRIS merchant beserta visualisasi *timeline tracking* 6 tahap pelacakan: 1. SUBMITTED, 2. PEMERIKSAAN, 3. PERSETUJUAN, 4. MENGIRIMKAN REQUEST KE ISSUER, 5. TANGGAPAN ISSUER: REJECTED/APPROVED, 6. DANA DIKEMBALIKAN. Log aktivitas pengawasan dipublikasikan ke Kafka Topic `hibank.qris.application.logs`. |
| Pre-condition | 1. Officer Bank Hibank telah berhasil login SSO dan memiliki hak akses ke menu *Dispute & Refund Management*.<br>2. Data pengajuan refund terdaftar pada tabel `refunds` dan `refund_tracking`. |
| Post-condition | 1. Sistem menyajikan daftar lengkap pengajuan refund transaksi QRIS dari seluruh merchant secara transparan.<br>2. Sistem menyajikan rincian detail pelacakan (*timeline tracking*) 6 tahap secara akurat mengacu pada record tabel `refund_tracking`.<br>3. Log aktivitas pemantauan dipublikasikan ke Kafka Topic `hibank.qris.application.logs`. |
| Trigger | Officer Bank Hibank mengklik menu **Monitoring Refund Transaksi**, menyaring data refund merchant, lalu mengklik tombol **"Detail"** pada baris refund terpilih. |
| Nama Tabel | refunds, refund_tracking, transaction_qris, audit_logs |
| Integrasi | 1. **Back Office Hibank Web UI:** Antarmuka pemantauan refund internal bank, filter multi-merchant, dan modal rincian *timeline tracking* refund.<br>2. **Dispute Management Service:** Microservice backend pengelola kueri data refund, rekapitulasi status, dan histori *timeline tracking* global.<br>3. **Apache Kafka Message Broker:** Centralized event broker log aplikasi topic `hibank.qris.application.logs`. |
| Asumsi | 1. Officer Bank Hibank memiliki kewenangan pemantauan lintas-merchant (*cross-merchant monitoring*) untuk kebutuhan audit operasional dispute.<br>2. Setiap tahapan pemrosesan refund oleh verifikator/approver bank maupun respon issuer secara *real-time* memperbarui record pada `refund_tracking`. |
| Keterbatasan | 1. Fitur ini bersifat *read-only* (hanya pemantauan dan pengawasan rincian detail pelacakan).<br>2. Akses terbatas khusus untuk pengguna internal Bank Hibank yang berhak. |
| Aturan Bisnis/Sistem | 1. **Cross-Merchant Monitoring Scope:** Back Office Hibank WAJIB menyajikan data pengajuan refund secara konsolidasi dari seluruh merchant QRIS terdaftar.<br>2. **Supported Refund Status Standard:** Status pengajuan refund pada tabel `refunds` yang wajib didukung dan ditampilkan badge kategorinya meliputi:<br>&nbsp;&nbsp;- **`IN_REVIEW`**: Pengajuan sedang dalam proses pemeriksaan awal bank.<br>&nbsp;&nbsp;- **`APPROVED_BY_BANK`**: Pengajuan telah disetujui oleh internal bank hibank.<br>&nbsp;&nbsp;- **`REJECTED_BY_BANK`**: Pengajuan ditolak oleh internal bank hibank.<br>&nbsp;&nbsp;- **`APPROVED_ISSUER`**: Pengajuan disetujui oleh penerbit instrumen (*issuer*).<br>&nbsp;&nbsp;- **`REJECTED_BY_ISSUER`**: Pengajuan ditolak oleh penerbit instrumen (*issuer*).<br>3. **6-Stage Refund Tracking Timeline Standard:** Tampilan detail pelacakan WAJIB menyajikan *timeline* progresive 6 tahap baku mengacu pada record tabel `refund_tracking` (`tracking_status`):<br>&nbsp;&nbsp;1. **`SUBMITTED`**: Pengajuan refund telah berhasil dikirimkan oleh merchant.<br>&nbsp;&nbsp;2. **`PEMERIKSAAN`**: Tahap pemeriksaan berkas & bukti transaksi oleh tim verifikator bank.<br>&nbsp;&nbsp;3. **`PERSETUJUAN`**: Tahap persetujuan otorisasi bertahap (*approver*) internal bank.<br>&nbsp;&nbsp;4. **`MENGIRIMKAN REQUEST KE ISSUER`**: Tahap transmisi request instruksi refund ke Pihak Issuer.<br>&nbsp;&nbsp;5. **`TANGGAPAN ISSUER: REJECTED / APPROVED`**: Tahap penerimaan respons jawaban dari pihak Issuer.<br>&nbsp;&nbsp;6. **`DANA DIKEMBALIKAN`**: Tahap penyelesaian pengembalian dana saldo/rekening pengguna.<br>4. **Centralized Kafka Application Logging:** Setiap akses pemantauan detail refund dipublikasikan ke Kafka Topic `hibank.qris.application.logs`. |
| Session Idle | 15 Menit |

# 2 Main Flow

**Tabel 2: Main Flow Monitoring Refund Transaksi**

| No. | Aktivitas | Deskripsi |
| ---: | --- | --- |
| 1 | Membuka Menu Monitoring Refund | Officer Bank Hibank melakukan login SSO dan mengklik menu **Dispute & Refund Management** -> **Monitoring Refund Transaksi**. |
| 2 | Menampilkan Daftar Refund Global | Sistem menampilkan halaman daftar pengajuan refund dari tabel `refunds` beserta filter status (`IN_REVIEW`, `APPROVED_BY_BANK`, `REJECTED_BY_BANK`, `APPROVED_ISSUER`, `REJECTED_BY_ISSUER`). |
| 3 | Filter / Cari Data Refund (Opsional) | Officer Bank memasukkan kata kunci pencarian (MID, Nama Merchant, RRN, ID Refund) atau memilih filter status refund. |
| 4 | Memilih Tombol Detail | Officer Bank mengklik tombol **"Detail"** pada salah satu baris pengajuan refund terpilih. |
| 5 | Request Detail & Tracking Data | Front-End mengirim request pencarian rincian detail refund beserta riwayat pelacakan ke API Gateway. |
| 6 | Query Database Refund & Tracking | Dispute Management Service mengambil rincian data dari tabel `refunds` (JOIN `transaction_qris`) dan mengambil histori urutan dari tabel `refund_tracking`. |
| 7 | Menampilkan Detail Timeline Tracking | Sistem menampilkan modal/halaman rincian detail refund yang menyajikan data transaksi dari `transaction_qris`, rincian refund, serta visualisasi *timeline tracking* 6 tahap (SUBMITTED, PEMERIKSAAN, PERSETUJUAN, MENGIRIMKAN REQUEST KE ISSUER, TANGGAPAN ISSUER: REJECTED/APPROVED, DANA DIKEMBALIKAN). |
| 8 | Publish Log ke Kafka Broker | Dispute Management Service mempublikasikan log aktivitas pengawasan ke Kafka Topic `hibank.qris.application.logs`. |
| 9 | Menutup Modal Detail | Officer Bank membaca rincian pelacakan dan mengklik tombol **"Tutup"**. |
| 10 | Use Case Selesai | Proses pemantauan dan pelacakan detail refund selesai dilaksanakan. |

# 3 Alternative Flow

**Tabel 3: Alternative Flow Monitoring Refund Transaksi**

| Kode | Alternative Flow | Deskripsi |
| --- | --- | --- |
| AF-01 | Data Refund Kosong | Pada langkah 2 atau 3, apabila belum pernah ada pengajuan refund merchant atau hasil filter tidak ditemukan, Sistem menampilkan pesan `Tidak ada data pengajuan refund`. |
| AF-02 | Data Tracking Tidak Ditemukan | Pada langkah 6-7, apabila detail refund ditemukan namun record `refund_tracking` kosong, Sistem menampilkan detail refund dengan keterangan `Riwayat pelacakan belum tersedia`. |
| AF-03 | Gagal Terhubung ke Database Server | Pada langkah 6, apabila koneksi database terputus total, Sistem mengembalikan HTTP status 500 dan Front-End menampilkan `Terjadi kendala internal pada server`. |

# 6 Sequence Diagram Monitoring Refund Transaksi

```plantuml
@startuml
title Sequence Diagram - Monitoring Refund Transaksi (Back Office Hibank)

actor "Officer Bank Hibank" as user
boundary "Front-End" as fe
control "API Gateway" as gateway
control "Dispute Management Service" as service
control "Kafka Broker" as kafka
database "QRIS Database" as db

user -> fe : Akses Menu Dispute & Refund Management -> Monitoring Refund Transaksi
fe -> gateway : Request Get Refunds List (status_filter, search_keyword)
gateway -> service : Teruskan Request Get Refunds List
service -> db : SELECT * FROM refunds WHERE refund_status IN ('IN_REVIEW', 'APPROVED_BY_BANK', 'REJECTED_BY_BANK', 'APPROVED_ISSUER', 'REJECTED_BY_ISSUER')
db --> service : Return Data Refunds List Payload
service --> gateway : Response Refunds List Payload
gateway --> fe : Response Refunds List Payload
fe --> user : Tampilkan Tabel Daftar Refund Global & Filter Status Badges

user -> fe : Klik Tombol "Detail" pada Row Refund Terpilih
fe -> gateway : Request Get Refund Detail & Tracking (refund_id)
gateway -> service : Teruskan Request Get Refund Detail

service -> db : SELECT r.*, t.* FROM refunds r JOIN transaction_qris t ON r.transaction_id = t.transaction_id WHERE r.refund_id = ?
db --> service : Return Refund Record & Transaction QRIS Detail
service -> db : SELECT * FROM refund_tracking WHERE refund_id = ? ORDER BY created_at ASC
db --> service : Return List Tracking Logs Payload

alt Data Valid & Found
  service -> kafka : Publish Event Log "hibank.qris.application.logs" (Payload: action = VIEW_REFUND_DETAIL, refund_id)
  kafka --> service : Confirm Event Logged
  
  service -> db : INSERT INTO audit_logs
  db --> service : Confirm Audit Log
  
  service --> gateway : Response Sukses (HTTP 200 OK - Detail & Tracking Payload)
  gateway --> fe : Response Sukses (HTTP 200 OK)
  fe --> user : Tampilkan Modal Detail Refund & Visualisasi 6-Stage Timeline Tracking
else Data Not Found [AF-01 / AF-02]
  service --> gateway : Response Error (HTTP 404 Not Found)
  gateway --> fe : Response Error (HTTP 404 Not Found)
  fe --> user : Tampilkan Pesan "Data refund tidak ditemukan"
end
@endl
```
