# 1 Deskripsi Use Case

**Tabel 1: Deskripsi Use Case Menghapus Parameter Blacklist FDS**

| Elemen Spesifikasi | Deskripsi Detail |
| --- | --- |
| ID Use Case | UC-BOH-034 |
| Nama Use Case | Menghapus Parameter Blacklist FDS |
| Penjelasan Singkat | Fitur Web Back Office Hibank pada menu FDS yang memfasilitasi User Bank (Fraud Risk Officer) untuk menghapus entitas/parameter dari daftar *Blacklist* (`fds_service`) sehingga pemblokiran otomatis terhadap nilai parameter tersebut dihentikan secara *real-time*. |
| Aktor Utama | User Bank (Fraud Risk / Anti-Money Laundering Administrator) |
| Aktor Pendukung | fds_service (Fraud Detection System Service) |
| Deskripsi Singkat | User Bank melakukan otentikasi login SSO ke Web Back Office Hibank dan mengakses menu **FDS** -> **Parameters**. Sistem menampilkan halaman pengelolaan parameter dengan beberapa tab. User Bank memilih tab **Blacklist**. Sistem menampilkan daftar parameter blacklist terdaftar beserta nilai (*value*), kategori, dan alasannya dari `fds_service`. User Bank memilih salah satu entitas parameter blacklist yang ingin dihapus, lalu mengklik tombol aksi **"Hapus"** (ikon tempat sampah). Sistem menampilkan modal konfirmasi penghapusan parameter blacklist yang meminta masukan **Alasan Penghapusan** (*deletion reason*). User Bank menginput alasan penghapusan dan mengklik tombol **"Konfirmasi Hapus"**. Front-End memvalidasi ketersediaan alasan dan mengirim request penghapusan ke API Gateway. Service `fds_service` memvalidasi keberadaan parameter pada repositori internal FDS. Setelah validasi sukses, `fds_service` menghapus (*soft delete* / merilis) record parameter blacklist tersebut dari repositori internal FDS serta memperbarui mesin aturan FDS secara *real-time* sehingga transaksi mendatang yang mencocoki nilai tersebut tidak lagi diblokir otomatis. Front-End memperbarui tabel daftar parameter blacklist dan menyajikan notifikasi konfirmasi sukses. |
| Pre-condition | 1. User Bank telah berhasil login SSO ke Web Back Office Hibank dan memiliki kewenangan otoritas *Fraud Risk Administrator*.<br>2. Parameter blacklist yang akan dihapus terdaftar aktif pada repositori internal `fds_service`. |
| Post-condition | 1. Parameter blacklist terpilih berhasil dihapus/dirilis dari repositori internal `fds_service`.<br>2. Aturan pemblokiran transaksi otomatis untuk nilai parameter tersebut dicabut secara *real-time*.<br>3. Alasan penghapusan dan ID pengapus tercatat pada jejak audit FDS.<br>4. Front-End memperbarui tampilan tabel tab Blacklist dengan menghapus baris parameter tersebut. |
| Trigger | User Bank mengklik menu **FDS** -> **Parameters**, memilih tab **Blacklist**, mengklik tombol aksi **"Hapus"** pada salah satu baris parameter, menginput alasan penghapusan, dan mengklik **"Konfirmasi Hapus"**. |
| Nama Tabel | Tidak dapat diekspose (Dikelola secara internal di dalam `fds_service`) |
| Integrasi | 1. **Web Back Office Hibank UI:** Antarmuka tab Blacklist pada halaman Parameters FDS, tombol aksi hapus, dan dialog konfirmasi penghapusan.<br>2. **fds_service:** Microservice terisolasi pengelola repositori blacklist, pencabutan aturan pemblokiran transaksi otomatis, serta penyedia API manajemen parameter FDS. |
| Asumsi | 1. Penghapusan parameter blacklist dilakukan apabila entitas telah dinyatakan aman atau masa sanksi/pemblokiran telah berakhir.<br>2. Seluruh nama tabel database dan repositori FDS terisolasi secara internal di dalam `fds_service` demi alasan keamanan arsitektur. |
| Keterbatasan | 1. Parameter blacklist yang sudah dihapus tidak dapat dihapus ulang.<br>2. Pengisian alasan penghapusan parameter bersifat mandatori untuk kebutuhan jejak audit (*audit trail*). |
| Aturan Bisnis/Sistem | 1. **Mandatory Deletion Reason:** Pengisian alasan penghapusan parameter blacklist (*deletion_reason*) bersifat WAJIB sebelum eksekusi penghapusan diproses.<br>2. **Internal Encapsulation Standard:** Data tabel internal `fds_service` DILARANG diekspose secara langsung ke Front-End; komunikasi wajib melalui API terisolasi.<br>3. **Immediate Rule Revocation Standard:** Setelah parameter berhasil dihapus dari `fds_service`, mesin aturan FDS WAJIB secara *real-time* menghentikan pemblokiran otomatis terhadap transaksi baru yang menggunakan nilai tersebut.<br>4. **Audit Trail Standard:** Setiap tindakan penghapusan parameter blacklist mencatat `deleted_by` (ID User Bank), `parameter_id`, `category`, `value`, alasan penghapusan, dan timestamp pada jejak audit FDS. |
| Session Idle | 15 Menit |

# 2 Main Flow

**Tabel 2: Main Flow Menghapus Parameter Blacklist FDS**

| No. | Aktivitas | Deskripsi |
| ---: | --- | --- |
| 1 | Membuka Menu FDS | User Bank melakukan login SSO dan mengklik menu utama **FDS**. |
| 2 | Memilih Menu Parameters | User Bank memilih sub-menu **Parameters**. |
| 3 | Memilih Tab Blacklist | User Bank mengklik tab **Blacklist** pada halaman Parameters FDS. |
| 4 | Menampilkan List Parameter Blacklist | Sistem menampilkan tabel daftar parameter blacklist dari `fds_service` beserta tombol aksi **"Hapus"** per baris parameter. |
| 5 | Memilih Tombol Hapus | User Bank mengklik tombol aksi **"Hapus"** pada salah satu baris parameter blacklist terpilih. |
| 6 | Menampilkan Modal Konfirmasi | Sistem menampilkan modal konfirmasi penghapusan yang memuat rincian kategori, nilai parameter, dan textarea Alasan Penghapusan. |
| 7 | Mengisi Alasan & Konfirmasi | User Bank menginput alasan penghapusan pada kolom textarea dan mengklik tombol **"Konfirmasi Hapus"**. |
| 8 | Memvalidasi Request Penghapusan | Front-End memvalidasi ketersediaan alasan dan mengirim request penghapusan parameter ke API Gateway. |
| 9 | Direct Remove & Revoke Rule FDS | Service `fds_service` menghapus parameter dari repositori internal FDS, menghentikan aturan pemblokiran transaksi *real-time*, dan mencatat audit log. |
| 10 | Menampilkan Konfirmasi Berhasil | Front-End memperbarui tabel daftar parameter blacklist dan menampilkan notifikasi bahwa parameter blacklist telah berhasil dihapus. |
| 11 | Use Case Selesai | Proses penghapusan parameter blacklist FDS selesai dilaksanakan. |

# 3 Alternative Flow

**Tabel 3: Alternative Flow Menghapus Parameter Blacklist FDS**

| Kode | Alternative Flow | Deskripsi |
| --- | --- | --- |
| AF-01 | Alasan Penghapusan Kosong | Pada langkah 7-8, apabila User Bank mengosongkan textarea alasan penghapusan, Sistem menolak request dan Front-End menampilkan `Alasan penghapusan parameter blacklist wajib diisi`. |
| AF-02 | Parameter Sudah Tidak Ditemukan | Pada langkah 9, apabila parameter blacklist yang akan dihapus sudah tidak ada pada repositori `fds_service`, Sistem membatalkan transaksi dan Front-End menampilkan `Data parameter blacklist tidak ditemukan`. |
| AF-03 | Service FDS Tidak Merespon / Timeout | Pada langkah 9, apabila `fds_service` mengalami kendala koneksi atau timeout, API Gateway mengembalikan HTTP 500/504 dan Front-End menampilkan `Gagal memproses penghapusan parameter blacklist pada fds_service`. |

# 6 Sequence Diagram Menghapus Parameter Blacklist FDS

```plantuml
@startuml
title Sequence Diagram - Menghapus Parameter Blacklist FDS

actor "User Bank" as user
boundary "Front-End" as fe
control "API Gateway" as gateway
control "fds_service" as service

user -> fe : Akses Menu FDS -> Parameters & Klik Tab "Blacklist"
fe -> gateway : Request Get Blacklist Parameters List
gateway -> service : Teruskan Request Get Blacklist Parameters List
service -> service : Query Internal Blacklist Parameters Data
service --> gateway : Response Blacklist Parameters List Payload
gateway --> fe : Response Blacklist Parameters List Payload
fe --> user : Tampilkan Tabel Daftar Parameter Blacklist

user -> fe : Klik Tombol "Hapus" pada Row Parameter Terpilih
fe --> user : Tampilkan Modal Form Konfirmasi Hapus (Show Param Info & Input Deletion Reason)

user -> fe : Input Alasan Penghapusan & Klik "Konfirmasi Hapus"
fe -> fe : Validasi Client-side (Alasan Mandatory)

alt Alasan Kosong [AF-01]
  fe --> user : Tampilkan Pesan "Alasan penghapusan parameter blacklist wajib diisi"
else Form Valid
  fe -> gateway : Request Delete Blacklist Parameter (Payload: parameter_id, deletion_reason)
  gateway -> service : Teruskan Request Delete Blacklist Parameter
  
  service -> service : Query & Validate parameter_id IN Internal Repository
  
  alt Parameter Not Found [AF-02]
    service --> gateway : Response Error (HTTP 404 Not Found)
    gateway --> fe : Response Error (HTTP 404 Not Found)
    fe --> user : Tampilkan Pesan "Data parameter blacklist tidak ditemukan"
  else Parameter Valid
    service -> service : Remove Parameter Record & Revoke Real-time Blocking Rule
    service --> gateway : Response Sukses (HTTP 200 OK)
    gateway --> fe : Response Sukses (HTTP 200 OK)
    fe --> user : Tampilkan Notifikasi Sukses & Refresh Tabel Tab Blacklist
  end
end
@endl
```
