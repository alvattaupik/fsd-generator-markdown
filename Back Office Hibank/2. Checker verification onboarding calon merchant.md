# 1 Deskripsi Use Case

**Tabel 1: Deskripsi Use Case Checker Verification Onboarding Calon Merchant**

| Elemen Spesifikasi | Deskripsi Detail |
| --- | --- |
| ID Use Case | UC-BOH-002 |
| Nama Use Case | Checker Verification Onboarding Calon Merchant |
| Penjelasan Singkat | Proses verifikasi dan pemeriksaan data permohonan registrasi calon merchant oleh User Checker melalui menu 4 Eyes Checker pada Back Office Hibank, mencakup validasi dokumen, kriteria kepatuhan eksternal/internal, pengelolaan data pada tabel `4eyes_requests` & `4eyes_request_histories`, hingga meneruskan berkas ke User Approver. |
| Aktor Utama | User Checker |
| Aktor Pendukung | - |
| Deskripsi Singkat | User Checker mengakses Back Office Hibank dan membuka menu "4 Eyes Checker". Sistem menampilkan daftar pengajuan onboarding calon merchant dari tabel `4eyes_requests` berstatus `NEED_ACTION`. User Checker memilih pendaftaran dan menekan tombol "Detail" untuk memeriksa seluruh data profil merchant, PIC, rekening settlement, dan dokumen pendukung. User Checker melakukan validasi kepatuhan mencakup Daftar Hitam Nasional (DHN) BI, Daftar Hitam Internal (DHI) Hibank, pedoman Anti-Money Laundering (AML), serta Daftar Terduga Teroris dan Organisasi Teroris (DTTOT) secara manual di luar sistem Hibank. User Checker memberi checklist "Terverifikasi" / "Tidak Terverifikasi" pada tiap item data di sistem, memasukkan catatan verifikasi (*checker notes*), dan menekan tombol "Submit". Sistem memperbarui data pada `4eyes_requests`, mencatat riwayat verifikasi ke `4eyes_request_histories`, mencatat rekam jejak pada `registration_trackings` (`step_name = 'CHECKING_BY_BANK'`), dan meneruskan permohonan ke antrean User Approver. |
| Pre-condition | 1. User Checker telah berhasil login ke Back Office Hibank menggunakan akun SSO dengan `role_id` Checker yang sah.<br>2. Terdapat permohonan registrasi calon merchant pada `4eyes_requests` dan `registration_requests` dengan status `registration_status = 'NEED_ACTION'`. |
| Post-condition | 1. Hasil pemeriksaan checklist data dan catatan verifikasi User Checker tersimpan pada `4eyes_requests` dan rekam riwayat ditambahkan ke `4eyes_request_histories`.<br>2. Status pendaftaran diperbarui dan rekam jejak ditambahkan pada tabel `registration_trackings` (`step_name = 'CHECKING_BY_BANK'`).<br>3. Permohonan registrasi calon merchant diteruskan ke antrean persetujuan User Approver (`WAITING_APPROVAL_BANK`). |
| Trigger | User Checker memilih detail pendaftaran calon merchant pada menu 4 Eyes Checker dan menekan tombol "Submit". |
| Nama Tabel | 4eyes_requests, 4eyes_request_histories, registration_requests, registration_request_merchant_details, registration_request_merchant_document_details, registration_request_merchant_pic_details, registration_trackings, audit_logs |
| Integrasi | 1. **Redis Cache:** Penyimpanan sesi login User Checker dan manajemen lock concurrency antrean pendaftaran. |
| Asumsi | 1. Pengecekan DHN BI, DHI Hibank, pedoman AML, serta DTTOT dilakukan secara manual oleh User Checker melalui sistem/portal eksternal resmi di luar sistem Hibank.<br>2. User Checker bertindak independen sesuai prinsip *4-Eyes Principle*. |
| Keterbatasan | 1. User Checker hanya dapat melakukan verifikasi dan meneruskan berkas ke User Approver, tidak memiliki wewenang untuk mengeksekusi keputusan akhir penolakan/persetujuan resmi ke PTEN.<br>2. Sistem Hibank tidak terhubung langsung secara otomatis (*direct integration*) ke database DHN BI, DHI, AML, dan DTTOT, sehingga hasil validasi bergantung pada input manual checklist User Checker. |
| Aturan Bisnis/Sistem | 1. **4-Eyes Principle & Data Isolation:** Setiap pengajuan verifikasi dikelola melalui entitas `4eyes_requests` dan `4eyes_request_histories`. Setiap pendaftaran calon merchant WAJIB melalui dua tahapan verifikasi terpisah: Tahap 1 oleh **User Checker** dan Tahap 2 oleh **User Approver**. User yang sama dilarang bertindak sebagai Checker dan Approver untuk pengajuan yang sama.<br>2. **External Compliance Checking Notice:** Pengecekan terhadap Daftar Hitam Nasional (DHN) BI, Daftar Hitam Internal (DHI) Hibank, pedoman Anti-Money Laundering (AML), serta Daftar Terduga Teroris dan Organisasi Teroris (DTTOT) dilakukan di luar sistem Hibank oleh User Checker.<br>3. **Mandatory Itemized Checklist:** User Checker wajib memberikan status checklist "Terverifikasi" atau "Tidak Terverifikasi" pada setiap kategori data (Data Usaha, Data PIC, Dokumen Legitimasi, dan Rekening Settlement) sebelum dapat melanjutkan submit.<br>4. **Mandatory Checker Notes:** User Checker wajib mengisi kolom catatan (*checker notes / remarks*) apabila terdapat penemuan ketidaksesuaian data.<br>5. **Workflow Handoff to Approver:** Penekanan tombol "Submit" oleh User Checker memperbarui status pada `4eyes_requests` dan `registration_requests` menjadi `WAITING_APPROVAL_BANK`, menambahkan entri riwayat pada `4eyes_request_histories`, serta menambahkan riwayat jejak audit pada tabel `registration_trackings` (`step_name = 'CHECKING_BY_BANK'`). |
| Session Idle | 15 Menit |

# 2 Main Flow

**Tabel 2: Main Flow Checker Verification Onboarding Calon Merchant**

| No. | Aktivitas | Deskripsi |
| ---: | --- | --- |
| 1 | Membuka Menu 4 Eyes Checker | User Checker membuka Back Office Hibank dan memilih menu "4 Eyes Checker" -> sub-menu "Verifikasi Onboarding Merchant". |
| 2 | Menampilkan Daftar Request Onboarding | Sistem menampilkan daftar permohonan registrasi calon merchant dari tabel `4eyes_requests` berstatus `registration_status = 'NEED_ACTION'`. |
| 3 | Memilih Detail Pendaftaran | User Checker memilih salah satu permohonan registrasi dari daftar dan menekan tombol "Detail". |
| 4 | Menampilkan Detail Data Onboarding | Sistem menampilkan detail lengkap data usaha, alamat, data PIC, dokumen pendukung, dan data rekening settlement calon merchant dari `registration_requests` & `4eyes_requests`. |
| 5 | Pengecekan Kepatuhan Eksternal | User Checker melakukan pemeriksaan data calon merchant terhadap DHN BI, DHI Hibank, pedoman AML, serta DTTOT secara manual di luar sistem Hibank. |
| 6 | Memilih Status Checklist Data | User Checker menandai opsi "Terverifikasi" atau "Tidak Terverifikasi" untuk masing-masing kategori data yang dicek pada form verifikasi sistem. |
| 7 | Menginput Catatan Verifikasi | User Checker memasukkan catatan verifikasi (*checker notes*) terkait hasil pemeriksaan data. |
| 8 | Mengirim Hasil Verifikasi | User Checker menekan tombol "Submit", Front-End mengirim data hasil verifikasi ke Onboarding Service via API Gateway. |
| 9 | Memproses Handoff ke Approver | Onboarding Service memverifikasi kelengkapan checklist, memperbarui `4eyes_requests` dan `registration_requests` (`registration_status = 'WAITING_APPROVAL_BANK'`), mencatat riwayat verifikasi ke `4eyes_request_histories`, serta menambahkan rekam jejak pada `registration_trackings` (`step_name = 'CHECKING_BY_BANK'`). |
| 10 | Use Case Selesai | Sistem menampilkan notifikasi sukses "Hasil verifikasi berhasil disimpan dan diteruskan ke User Approver" dan memperbarui tampilan daftar permohonan. |

# 3 Alternative Flow

**Tabel 3: Alternative Flow Checker Verification Onboarding Calon Merchant**

| Kode | Alternative Flow | Deskripsi |
| --- | --- | --- |
| AF-01 | Checklist Data Belum Lengkap | Pada langkah 8, apabila terdapat kategori data yang belum diberi status "Terverifikasi" / "Tidak Terverifikasi", Sistem menolak submit dan Front-End menampilkan `Seluruh kategori data wajib diberi status verifikasi sebelum dikirim.`. |
| AF-02 | Catatan Checker Kosong pada Data Tidak Terverifikasi | Pada langkah 8, apabila User Checker memilih "Tidak Terverifikasi" namun tidak menginput catatan verifikasi, Sistem menolak submit dan Front-End menampilkan `Catatan verifikasi wajib diisi apabila terdapat data yang tidak terverifikasi.`. |
| AF-03 | Permohonan Sedang Diperiksa Checker Lain (Lock Conflict) | Pada langkah 3, apabila permohonan pada `4eyes_requests` sedang dibuka/diperiksa oleh User Checker lain, Sistem menolak akses detail dan Front-End menampilkan `Permohonan ini sedang ditangani oleh Checker lain.`. |
| AF-04 | Pelanggaran Prinsip 4-Eyes (User Sama dengan Initiator/Approver) | Pada langkah 8, apabila User Checker mencoba memeriksa pengajuan yang diinisiasi oleh dirinya sendiri, Sistem menolak dan Front-End menampilkan `Akses ditolak. Pengguna dilarang memeriksa pengajuan yang diinisiasi sendiri (4-Eyes Violation).`. |

```plantuml

fe -> gateway : GET /api/v1/hibank/onboarding/checker/list
gateway -> service : Fetch daftar permohonan onboarding

service -> db : SELECT e.*, r.registration_number FROM 4eyes_requests e JOIN registration_requests r ON e.registration_request_id = r.id WHERE e.registration_status = 'NEED_ACTION'
db --> service : Return List Permohonan 4eyes_requests (NEED_ACTION)
service --> gateway : 200XX00 (Success Fetch List)
gateway --> fe : 200XX00 (Success Fetch List)
fe --> checker : Tampilkan Daftar Permohonan Onboarding

checker -> fe : Pilih Permohonan & Klik "Detail"
fe -> gateway : GET /api/v1/hibank/onboarding/checker/detail/{registration_id}
gateway -> service : Fetch detail permohonan

service -> db : SELECT r.*, m.*, d.*, p.*, e.* FROM registration_requests r JOIN 4eyes_requests e ON r.id = e.registration_request_id JOIN ...
db --> service : Return Data Detail Merchant, PIC, Dokumen & Rekening
service --> gateway : 200XX01 (Success Fetch Detail Data)
gateway --> fe : 200XX01 (Success Fetch Detail Data)
fe --> checker : Tampilkan Halaman Detail & Form Checklist

checker -> checker : Pengecekan DHN BI, DHI Hibank, AML, & DTTOT (Manual di Luar Sistem Hibank)
checker -> fe : Pilih "Terverifikasi"/"Tidak Terverifikasi", Input Catatan Checker & Klik "Submit"
fe -> gateway : POST /api/v1/hibank/onboarding/checker/verify (registration_id, checklistData, checkerNotes)
gateway -> service : Teruskan hasil verifikasi Checker

service -> service : Validasi Kelengkapan Checklist & Catatan Checker

alt Checklist Belum Lengkap / Catatan Kosong [AF-01 / AF-02]
  service --> gateway : 400XX00 (Checklist / Notes Incomplete)
  gateway --> fe : 400XX00 (Checklist / Notes Incomplete)

else Data Verifikasi Valid
  service -> db : BEGIN TRANSACTION
  service -> db : UPDATE 4eyes_requests SET registration_status = 'WAITING_APPROVAL_BANK', updated_by = ? WHERE registration_request_id = ?
  service -> db : UPDATE registration_requests SET registration_status = 'WAITING_APPROVAL_BANK' WHERE id = ?
  service -> db : INSERT INTO 4eyes_request_histories (4eyes_request_id, action_type, remarks, created_by) VALUES (?, 'CHECKER_VERIFY', ?, ?)

  service --> gateway : 200XX02 (Checker Verification Submitted & Handoff to Approver)
```
